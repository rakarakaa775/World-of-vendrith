## What it is

No AI Slop is an open-source writing/editing skill intended to reduce generic or formulaic AI-writing patterns while preserving the writer's meaning, vocabulary, cadence, humor, uncertainty, and personal voice. It supports two distinct modes:

1. Edit: make the minimum effective changes, preserve the author's intent, and report what changed.
2. Detect: identify named patterns in a supplied text, quote the relevant lines, and suggest concise fixes without rewriting the text or guessing whether AI authored it.

Its documented checks cover patterns such as formulaic binary contrasts, throat-clearing openings, faux-insight setups, inflated importance claims, unsupported vague attribution, repetitive sentence shapes, and generic conclusions. Its evaluation checklist also emphasizes factual preservation, concrete details, active voice, proportional editing, and retaining distinctive writing.

## Why it may matter to Vendrith

Vendrith uses AI-assisted development and maintains architecture contracts, audits, status logs, implementation plans, and user-facing explanations. A lightweight writing review can help those documents stay specific, verifiable, and readable rather than padded with generic claims or repetitive summaries.

The useful target is the quality of written communication—not the validity of code, architecture, tests, security controls, or licensing decisions.

## Vendrith decision

**ADAPT**

Adapt the principles into Vendrith's documentation/review workflow. Do not treat the external skill as a required runtime dependency, a universal ban list, or proof that text was generated by AI.

## Relevant practices

| Practice | Relevance | Decision | Notes |
|---|---|---|---|
| Preserve meaning and author voice | Keeps project decisions and user intent intact | ADAPT | Especially important for Indonesian-language notes and informal developer conversations |
| Minimum effective edit | Avoids rewriting already-clear docs merely for uniformity | ADAPT | Edit only when clarity, accuracy, repetition, or specificity improves |
| Concrete and verifiable claims | Useful for audits, test reports, status updates, and architecture docs | ADAPT | Attach files, test commands/results, commit IDs, dates, or evidence where available; never invent evidence |
| Detect patterns without asserting authorship | Helps reviewers flag style problems without unreliable AI-detection claims | ADAPT | Report observable writing patterns; do not label a document AI-written |
| Self-check after editing | Encourages a final pass for meaning, specificity, and voice | ADAPT | Treat checklist items as prompts for judgment, not rigid scoring |
| Automatic rewriting of all project docs | Could introduce unnecessary diffs or alter established contracts | DEFER | Review targeted documents only when needed |
| Install the skill globally or add it as a dependency | Not required to benefit from its principles | DEFER | No installation or dependency change was made by this audit |

## Conflicts with Vendrith

- A style checklist cannot replace technical validation, code review, tests, security review, source citations, or license review.
- A phrase that resembles an AI-writing pattern is not by itself proof of AI authorship or low-quality writing. Context matters; a contrast or colon can be perfectly appropriate.
- Do not invent metrics, examples, sources, test results, commit hashes, or implementation status to make prose sound concrete.
- Do not flatten the user's Indonesian voice into overly formal or generic English.
- Do not run broad rewrites over architecture contracts or audit history merely to normalize style. Preserve technical meaning and historical evidence.
- Do not use this reference as a gate that blocks implementation or changes runtime behavior.

## Implementation impact

Suggested lightweight use in Vendrith:

1. Apply the principles when drafting or revising user-facing explanations, reference audits, roadmap summaries, and status reports.
2. For implementation audits, keep a clear separation between observed evidence, inference, recommendation, and unverified status.
3. Before finalizing edited prose, check that the original meaning remains intact, claims are supported, repetition is reduced only where useful, and the author's voice remains recognizable.
4. Keep technical verification independent: run the relevant tests and inspect source files instead of treating polished prose as evidence.

Potential documentation locations to consider later: `inspirasi/README.md`, `docs/architecture/`, and relevant audit documents. This audit does not change those other documents or establish a new mandatory repository-wide instruction.
